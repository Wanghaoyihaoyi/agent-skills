# CI 历史、收益与稳定性

方法参考：Rodrigo Roim，OpenAI，[Maintaining software with the GPT-6 family](https://developers.openai.com/blog/maintaining-software-with-the-gpt-6-family)（2026-10-14）。只在用户要求 CI 优化或偶发失败排查时使用；不把普通故障排查扩大为全仓 CI 改造。

## 按历史收益排序

先取得约定范围近期 CI 运行与 job/step 记录，注明仓库、分支、工作流、时间窗口、样本数和缺失记录。必要时分页，不能用 API 第一页代表全部近期运行。区分触发事件、矩阵、重跑、取消、缓存命中、执行器规格、排队和实际执行耗时；检查任务依赖及合并所需检查。缺少历史权限或记录时，给出待验证假设，不编造每日节省数。

优先核查重复触发和重复工作、无效矩阵、缓存失效、依赖安装与构建复用、分片失衡、昂贵夹具、意外真实网络调用，以及失败导致的重跑。改变触发路径、任务依赖或缓存时，保留跨模块变更覆盖、所需检查的完成语义和缓存正确性。不能通过跳过必要测试、隐藏失败或扩大重试来降低表面负载。

按历史频率估算：每日节省机器分钟 = 每日受影响执行次数 × 每次可省执行分钟，扣除新增预处理、缓存或调度成本。矩阵与重跑只计算一次，多个方案共用同一份收益时注明重叠，不直接相加。区分原始机器分钟、计费分钟或货币成本；计费换算使用实际平台口径，不能把执行器价差混进时间收益。

用表格按预计每日节省机器分钟降序列出：方案、历史依据、频率与单次节省假设、每日节省范围、置信度、风险和验证办法；未知收益另列为待测。另报开发者等待时间或关键依赖路径的收益：并行任务分钟总和不同于整条流水线完成时间，增加并行可能只缩短等待却增加机器成本。

用户只问建议时交付排序表。实施已授权时先选收益和风险相称的小批次，用相近变更、执行器和缓存条件对照；报告实测与原估算差异，必要时给中位数、尾部耗时和波动。一次快跑不证明每天节省成立。

## 偶发失败：修复明确原因

按测试名与失败签名聚合近期运行，保留运行链接、提交、环境、首次失败和重跑结果；区分产品回归、测试隔离或时序问题、执行器资源不足及外部依赖故障。同提交同环境下失败后成功是线索，单次重跑通过不能证明根因或修复；确定性失败不能仅贴 flaky 标签。

优先处理证据清楚、范围可控的问题。对时间依赖、共享状态泄漏、随机种子、竞态或未隔离的网络调用提出可检验假设，用日志、受控时序或隔离复现证明原因；只有不属于测试目标的外部依赖才适合模拟，不把真实集成合同一起 mock 掉。不要用延长 sleep、吞异常、降低断言、删除测试或无限重试掩盖失败。

测试新增或改写遵守 [test-audit](../../test-audit/SKILL.md)，复用已有证明。能稳定复现时，展示旧版因目标原因失败、修复后通过；难以复现时报告旧/新版本的重复运行次数、失败数、环境和种子或顺序，零失败只代表本次样本。最终运行相关整组测试，检查顺序污染与断言仍有效，而非仅反复跑单个样例。

批量任务先扫描约定范围，再完成能找到明确修复的简单问题；复杂或证据不足的项逐项记录缺口，不为穷尽所有 flaky 测试无限扩张。修复成功后按实际授权提交或建 PR，未验证成功的尝试不当作已修复交付；报告扫描范围、已修复、仍未解决和未覆盖项。
