# Patch Audit

执行本 skill 时，首条进度消息以 `🍮` 开头，例如：`🍮 开始复审本轮补丁的必要性。` 显式调用和自动选用都适用。仅创建、编辑或解释本 skill，不代表执行代码复审。

完成实现后，先验证本次功能及受影响的主流程，再复查本次改动引入的抽象、分支、状态和依赖是否必要，按证据决定保留或简化。不要默认必须删减或合并；没有合理候选时允许不改。用户只要求整理、简化或保持行为不变时，仅执行等价简化，不顺便修复功能缺陷或改变产品行为；用户要求只读时，仅报告。

## 提交前自动触发

每次代理准备执行 Git 提交时，必须先执行本 skill，不要求用户显式调用；适用于普通提交、修改上一笔提交（`git commit --amend`），以及其他工具代为创建或修改提交的操作。自动触发不提供提交授权，仍遵循当前任务和项目的授权边界。

以本次实际待提交内容为审查对象。已经暂存时按 `--staged` 检查；尚未暂存时先确认本任务准备纳入的改动，提交前再核对最终暂存差异。纯文档、配置或技能修改也检查必要性与冗余，按内容选择验证方式，不强套代码重构流程。

同一份待提交内容已经完成本轮审查和验证时，可复用结果，不重复执行。审查后又有修改或暂存范围改变，补审变化及受影响部分；修复后完成相关验证，再核对最终待提交内容。一次任务分成多笔提交时，每笔都需要对应的审查结论。

发现阻止提交的问题时先在授权范围内修复；无法安全修复或缺少必要验证时，明确阻碍并暂缓提交。检查通过后继续已授权的提交流程，不额外索要确认，也不因本 skill 自行创建提交。此触发由加载该 skill 的代理执行，不是 Git hook，无法拦截用户在终端或其他未加载该 skill 的工具中提交。

## 范围与基线

读取适用的项目规则，确认当前目录、分支、`git status --short --branch` 及本任务的改动归属。审查本轮 diff 和直接关联的旧实现；范围不明时先查任务上下文，不把整个工作区都当成本任务。

范围参数表达审查意图，不是独立 shell 命令：

- `$patch-audit`：当前任务相对 `HEAD` 的暂存与未暂存改动，并纳入相关未跟踪文件。
- `$patch-audit --staged`：仅以暂存改动为起点。
- `$patch-audit src/foo.ts src/bar.ts`：限制到指定文件的本轮改动。
- `$patch-audit --ref=main`：相对指定引用比较，可组合路径和 `--staged`；已提交任务使用确认的提交范围。

读取差异用 `git diff --no-ext-diff --no-textconv HEAD -- [paths...]`；暂存模式加 `--cached`。引用先用 `git rev-parse --verify --end-of-options '<ref>^{commit}'` 解析为提交 ID，再替换基线。路径正确引用并放在 `--` 后。无 `HEAD` 的新仓库按新增内容检查；引用无效则报告，不擅自换基线。未跟踪文件另查 `git ls-files --others --exclude-standard`。

记录开始时的内容与改动块。暂存与未暂存修改交叠时，对照两个版本确认归属，不能直接套用暂存区行号。所有编辑写入工作区，保持已有暂存状态；生成文件遵循项目生成流程。范围为空就结束，不自动退回上一笔提交或扩大到全仓。

暂时放下实现过程，从原始需求、根因及实际调用链重建目标行为和必要约束。自己或其他 Agent 刚写的代码、现有测试，都不是最终设计正确的证明。

## 判断必要性

以本次改动引入的抽象、分支、状态和依赖为对象，包括新增的判断条件、定时器、重试、事件、中间层和兼容逻辑；关联旧实现用于查明原因，不因此扩大清理范围。逐项检查：

- 它解决原始问题，还是修补上一层实现造成的副作用？
- 能否在更明确的责任边界一次解决？有没有更小、更直接的改动，让这批新增逻辑一起消失？
- 旧逻辑是否已被替代却未删除？兼容分支是否只为迁就本轮尚未同步修改的内部代码？

重点追查“新增标记 → 补同步 → 加锁或延迟”的补丁链。用调用链、合同、历史或运行证据说明每个环节对应的真实约束；不预先认定锁、重试、延迟有错，也不把外部版本兼容误当成内部遗留。

### 新增复杂度的举证责任

新增抽象、状态、配置或依赖时，说明它保护的已确认需求、直接方案会失败的具体场景，以及新增的维护、同步和运行成本。这是复杂度预算：以真实收益约束复杂度，不设统一行数、层数或数量指标；不能用未经确认的未来需求支付今天的成本。

做反事实分析：如果不用这个机制，只复用现有能力或在责任边界直接处理，哪个实际需求无法满足？代码和合同已能回答时，不另造实验。收益仍存疑时，再按下述消融规则取得运行证据。新增机制承担收益举证责任，删除机制承担必要行为验证责任。无法解释收益的新增设计先缩减；现有保障证据不足时先保留，不把缺少测试当成无用证据。

### 判断通用修复还是场景补丁

把用户的原始目标、已确认的业务规则、历史补丁及本轮改动放在一起判断。先用一句话说明：这次改动想保证什么行为，问题由什么机制产生，哪些场景受同一机制影响。改动意图是待验证的假设，不能用作者的说明代替代码和运行证据；意图或根因不明时先查上下文，仍无法确认就标明证据不足。

“通用”指在正确的责任边界处理同一类问题，不是支持所有未来场景，也不要求建立通用框架。按有独立目的的改动分别判断；同一份补丁可能既有共性修复，也有场景补丁。

- **共性根因修复**：判断条件来自业务规则、接口合同或资源归属，在实际产生副作用的边界生效；同一根因换个入口、对象或发生顺序，规则仍然成立。
- **合理的限定特例**：只适用于某个场景，但范围由明确需求、业务规则或真实外部兼容约束决定，有依据和边界。影响一个场景不等于死板补丁；临时兼容还应说明移除条件。
- **场景补丁**：只认报错样例中的文案、对象、入口、顺序或固定延迟，绕开症状而未处理共同原因；相邻场景仍会失败，下一种情况还要继续加分支。这些写法是排查线索，不是单凭形式判错的理由。

做一次有依据的反向检查：保持根因不变，换一个实际存在的相邻入口、输入、状态或时序，当前修复是否仍有效？再检查根因不成立的正常场景，会不会被误拦或改变业务行为。沿相关调用链和同类模块找证据；不要为假想需求扩大范围，也不要把不同业务规则强行合并。

例如，旧请求返回后覆盖新请求的结果，应检查结果写入处是否验证请求归属，以及其他入口是否同样受保护；仅忽略某句返回文案，通常没有解决共同原因。反过来，合同明确要求某类订单采用不同价格规则，限定该类订单的分支可以是正确实现。

结论要说明类别、依据和覆盖边界。确认是场景补丁时，优先在根因处用最小改动替换，并清理由此失效的例外；只读或仅等价简化任务中仅报告，不擅自改变行为。无法确认时保留必要保障并指出缺少的证据，不硬判“通用”或“死板”。

### 按需消融验证

只有对某个机制的实际收益存疑，且能建立有效对照时，才做小范围消融验证，即暂时停用或简化该机制，观察它实际带来的作用。这不是每次复审的必做步骤。

保留可恢复、可比较的基线，一次只停用或简化一个机制，用相同场景比较正确性、延迟、成本及该机制相关的失败场景。不要用正常路径通过证明保障逻辑无用；无法覆盖它要防范的失败或关键时序，就不能据此删除。不要为实验新建通用框架或扩大重构范围，实验本身也须遵守现有授权和副作用边界。

结论允许保留、删除或证据不足，不能预设删减目标。没有实际运行的对照，只能称为分析或待验证，不得称为已完成消融实验；已运行时说明基线、单项变化、对照场景、实际结果及证据缺口。实验版本通过不代替最终版本验收，最终保留的版本仍须通过相关检查。

## 收敛与简化

证据充分时，在根因所属边界直接收敛实现，删除失效的补丁和被替代的旧逻辑，同步必要的调用方与测试。只修改确认属于本任务的内容；调整关联旧实现也必须在本任务范围内。归属不明或与他人改动混杂时，先只读检查该部分，继续处理可隔离的内容。不得整体回退工作区、覆盖或暂存他人改动。

沿用已有授权，不扩大提交、推送、部署或外部操作权限。无需新增治理框架，也不为显得做了复审而强行改代码。

必须保留的复杂度，说明真实约束；临时保留的补丁，说明保留原因和移除条件。证据不足时明确缺口，不猜测根因后贸然删除保障。

对保留代码减少不必要的嵌套、重复判断、冗余状态和无价值抽象，改善局部命名，复用已有能力。等价简化须保持功能、公开接口、副作用顺序、异常语义和必要保障；与修正已确认错误行为区分说明。

优先清楚的控制流，不追求行数，不引入嵌套三元或过于巧妙的写法。保留解释业务规则、设计理由和非显然行为的注释。已有合理结构无需强改。

仅做等价简化时，只编辑原定改动块；新增文件可处理整文件。按初始内容追踪范围，不机械沿用编辑前行号。可读取周边代码，但不扩成整文件重构；需要范围外改动时留下建议。删除、纯重命名和二进制变更不做文本简化。

## 验证

检查最终差异及 `git diff --check`，确认归属和范围。按风险运行相关测试、类型或静态检查，以用户可观察行为及必要可靠性保障验证结果，覆盖相关正常路径、异常和关键时序；不为等价重写堆砌测试。

修复验证应能区分原错误与目标行为，等价简化验证原有行为与保障继续成立，不把实现细节当验收标准。删除旧实现专属测试时，承接仍有效的行为约束；不靠放宽断言或过度模拟证明成功。区分已有失败和本次引入的问题，未运行或未通过的检查如实报告。没有修改时，可复用本次功能及受影响主流程的有效验证证据，不为纯整理额外运行测试；缺少的验证如实报告。

涉及共性修复或场景补丁替换时，验证原问题、同一根因的代表性相邻场景，以及不应受影响的正常行为；优先复用已有证据和检查，只在存在关键缺口时补充验证。不以原报错样例通过，或断言与实现一致，证明修复已经覆盖同类问题。

## 交付

简短说明：关键改动属于共性根因修复、合理限定特例、场景补丁还是证据不足，并给出依据和覆盖边界；消除了哪些补丁、根因现在在哪里解决；保留代码如何变清楚；哪些复杂度仍有真实价值或暂时保留；验证证据与未验证部分。仅做简化时省略不适用项。没有有价值且安全的修改时，直接说明依据。
