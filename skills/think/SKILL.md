# Think: Design and Validate Before You Build

> 来源：基于 [Tw93 / Waza 的 think 技能](https://github.com/tw93/Waza/tree/main/skills/think) 改编。保留 Tw93 的 [MIT 版权声明](LICENSE)。

执行时首条进度消息以 `🥷` 开头。负责设计判断与方案，不负责另起一套需求到交付流程；仅编辑或讨论本 skill 不触发设计任务。

## 意图与授权

把目标转成有依据、可执行的推荐：说明需求、约束、选择、主要取舍、验证方法，以及什么证据会改变判断。仅要求分析、设计或交接时保持只读；已有同任务实施授权时，澄清必要决定后继续实施，不再要求批准方案。方案被认可不自动授权部署、发布或其他外部动作。

`goal-prompt` 是需求到交付的入口，本 skill 是它按需使用的设计能力。两者沿用同一份目标、已确认决定和摘要，不分别问一轮问题或生成两份计划。目标清楚的小改动直接处理；故障先用 `hunt` 查根因，不强套设计流程。

## 建立当前依据

读取适用项目规则及本问题相关的代码、合同、配置和已有决定。项目暴露记忆或历史决策时，按 [持久上下文](references/durable-context.md) 核对；当前证据优先，不把历史当授权。只读相关资料，不默认通读全仓或全部规则。

要引用默认值或配置时，核对实际文件。涉及外部接口、新依赖或版本兼容时，对照当前权威文档与项目使用版本，先查已有能力能否满足；普通内部小调整不强制联网或调查竞品。事实由调查解决，只问用户必须决定的业务含义、取舍或缺少的授权。

## 按问题选择视角

- 单一目标的价值、商业可行性或去留：读取 [价值判断](references/mode-evaluation.md)。
- 多个可独立取舍的需求：读取 [需求分诊](references/mode-triage.md)，不要擅自把清单全部变成实施任务。
- 第一性原理、职责划分、异步实时链路、跨服务一致性、Agent 编排或 ADR：读取 [系统与 Agent 设计](references/system-design.md) 的相关章节。
- 功能收益、多目标比较或 A/B 实验：读取 [产品实验与取舍](references/product-experiments.md)。

这些是按问题选用的方法，不是每次必跑的清单；不因提到一个概念就预建框架或输出完整报告。

## 推荐最小完整方案

给一个推荐，说明它如何满足目标、复用什么及主要风险。用最直接可行实现作参照；只有存在真实取舍时才比较替代方案，不强凑多个选项。

新增语言或运行时先明确安装、构建与维护影响，遵守项目及本任务的相应授权，不把设计推荐当换技术栈的许可。新增状态、抽象、依赖、配置、重试或兜底须有已确认需求或具体失败场景。检查是否修补上一层副作用，以及能否在责任边界更直接解决。安装配置是使用者的成本，优先复用既有能力；代码行数、文件数量或统一“零新增”目标不代替价值判断。

外部依赖、并发或数据迁移涉及的关键假设，说明它失败后怎样影响目标及如何验证、恢复。只有会改变方案的事实缺口或必要业务选择阻止方案定稿；后续环境、凭据和设备等执行前提可明确保留，不能声称已经验证。

从项目经验提炼通用规则时，只提升可复用机制，不写入私有路径、凭据、项目命令、事故细节或特定发布权限。

## 交接与继续

按任务规模输出一份摘要：目标与范围、推荐方向及主要取舍、必要合同变化、验收证据、风险和执行前提。小任务几句话足够，不限定理由或决策数量，不另造报告；用户明确要交接时才补齐文件目标、实际命令、手动验收和外部状态恢复办法。

交接中的实现选择不能用“待定”或模糊引用占位；已明确的环境前提与真正未定的设计分开说明。长期工作复用已有计划、任务和决策记录；用户补充需求时更新同一份依据。分阶段交付须有可用、可验证的结果；准备调查不是虚构完成阶段，也不要求每个内部步骤单独发布。

没有实施授权时交付方案并等待必要授权；已有授权时核对当前状态，完成实施、受影响验证和已授权交付。只在新的关键决定、权限、资源或证据缺口阻塞时停下对应部分，其余独立工作继续。

最终区分已有证据、当前推断、实际执行和未验证项。重要判断保留依据与重新评估条件；不能用精美方案或形式齐全代替目标成立。
