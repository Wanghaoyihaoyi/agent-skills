# 发布判断与交付

在现有授权范围内执行；询问是否值得发版是只读分析，不是发布授权。不要把一种仓库的版本规则、托管平台或部署方式套到所有项目。

## 是否值得发版

确认用户指定版本或实际已发布版本为比较基线，检查用户能感知的改动、修复、兼容影响与风险。给出发布或暂缓的理由；项目采用语义化版本时，按其规则建议版本变化，不凭提交前缀机械决定。

## 已授权交付

1. 从项目规则确认本次动作、目标分支、环境或发布渠道，以及必须完成的审核与验证。将提交、推送、构建、上传、部署、评论、关闭或合并分别列入适用范围。
2. 使用 [发布清单](project-context.md) 核对适用的证据。可用 `python3 <skill-base-dir>/scripts/release_gate.py --root <project>` 收集只读本地信号；该脚本不会刷新远端，仍需真实远端证据。
3. 必要审查由 `code-review` 完成。已有相关验证且目标未变时，不重复跑整套流程。准备具体产物与审查结果后，仅对尚未授权的动作请求最终决定。
4. 按项目规则检查版本、生成文件、包内容、所需资源及可执行权限。发布包内新增的脚本和引用要从实际安装位置能找到；只检查源码不够。仅提交源码时不强制发布打包流程。
5. 写发布说明前读取项目实际发布惯例。说明真实用户结果，保持语言和格式；所述能力必须在候选产物中。必要时使用 `write`。
6. Git 操作遵守主文件的工作区边界。提交前审核暂存差异；推送前刷新远端并确认待推送提交没有夹带。遇到并发变化重新核对，不擅自重置、隐藏工作或强推。
7. 只向授权的账号、仓库、分支、环境和渠道交付。预览版与正式版分别核对；不同发布面可能在不同时刻上线，特别区分自动部署的服务端与待发版的客户端。
8. 发布后按任务要求读回远端、CI、包仓库、下载资源或部署状态。用实际版本、内容或校验信息验证，不能只凭页面标题、文件大小或工作流绿灯宣称产物正确。

结果未知的创建、上传或发布动作先查询终态，不为让检查变绿重复执行。反复查询没有新证据时，报告具体阻塞和下一步，不无限等待。

涉及 issue/PR 的回复和关闭时读取 [回复操作](public-reply.md)。只有明确要求发布表情或其他附加动作时才做，不从“发布完成”推定授权。

对反复修订或取消后恢复的候选版本，读取 [产物与发布面](release-surfaces.md) 的对应章节，分别判断是否适合继续预览测试、是否适合正式发布。

最终核对每个已授权动作。说明可追溯的提交、目标远端、CI、产物和验收状态；不适用项省略，缺证据的项保留为未验证。
