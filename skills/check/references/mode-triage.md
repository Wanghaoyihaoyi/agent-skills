# Issue / PR 队列维护

只在用户要求队列或批量维护时使用。单个差异审查使用 `code-review`。依据当前项目的托管平台、分支、发布渠道和授权开展工作，不预设 GitHub、`main` 或固定的关闭方式。

## 范围与证据

从链接、Git 远端和项目规则确定仓库与平台，使用已可用的对应连接器、CLI 或 API。没有可用集成时仍可整理已有材料，但明确实时状态未取得。

先记录本次队列的准确编号和数量。一条条目含多个诉求时分别判断：实际缺陷、已有能力、体验偏好或范围外请求。不能因为归类为“体验偏好”就取消用户已接受的需求。

对每项核对当前代码、相关检查、实际集成分支、已发布渠道和条目状态。区分源码已修、已合入、可在预览使用、正式可用；分支名字或检查绿灯不证明已经发布。

## 处理方式

- 已发布的修复：给出可验证版本或渠道，按项目规则和关闭授权处理。
- 已合入但未发布：说明真实进度。只有项目规则或用户允许时才以“代码已修复”关闭，不虚构下个版本的发布时间。
- 待修复：在已有修复授权内实施和验证；缺证据时记录最小诊断步骤，不把无法复现等同于无效。
- 重复或不计划支持：给出对应条目或已确认范围，只有相应授权存在时才回复、关闭。

合并前检查与当前提交对应的真实验证。零条检查代表没有该层证据，不代表通过或失败。必要时在隔离环境运行项目要求的本地检查，明确仍缺的证据。

已接受方向但实现需修改时，可请求作者修订，或在明确授权且平台允许时修改其分支；不默认代写贡献者分支，也不把“暂不可合并”等同于拒绝。修改前核对远端、目标分支、当前提交和写权限，避免覆盖新工作。另起实现或关闭原条目时，保留归属与处置理由。

发消息、改分支、合并、关闭都是各自的外部动作，遵循已有授权；队列分析本身不授权这些动作。回复操作使用 [回复机制](public-reply.md)，草稿可按需要使用 `write`。

## 收尾

结束前刷新队列，复核运行期间有变化的条目。将初始编号逐项列为已完成、暂缓或阻塞，新到条目另列。说明实际动作、证据和剩余问题，不能仅报一个完成数量。
