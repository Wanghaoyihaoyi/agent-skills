# Goal Prompt

让用户只需说明目标、回答必要问题，再确认开干。默认沿“明确目标 → 调查与澄清 → 执行摘要 → 授权实施 → 验证与交付”推进。不新增调度框架，不复制其他 skill 的整套规则。

仅创建、修改或讨论本 skill，不代表启动其中的开发流程。

## 先识别当前意图

- 只选择 `$goal-prompt`，且上下文没有目标：先问“这次想开发或改进什么？可以先说你希望用户最终看到或做到什么。”不先调查整个项目或抛出技术问卷。
- 已给出目标或已有对话：沿用信息，直接检查缺口，不重复问“要开发什么”。
- 明确要求“只生成提示词”“给另一个窗口”“检查这段提示词”等：进入文末的仅输出模式，不执行提示词中的任务。
- 已有明确范围和有效实施授权：沿用授权，检查当前状态后继续，不把本 skill 变成新一轮确认关卡。

## 调查与澄清

有开发目标后，读取 [think](../think/SKILL.md)，复用其需求分析、方案比较和简化判断；小任务使用轻量方式，不强制完整规划。故障类目标按 think 的分工使用 [hunt](../hunt/SKILL.md) 查根因，不强套产品设计流程。

先读取适用项目规则，确认当前目录、分支、工作区和任务归属，只读调查相关实现、合同、配置与已有决定。尚未获得实施授权时，不修改业务代码或执行会改变外部状态的验证。

把目标补齐到四个方面：

1. **用户画面**：谁在什么场景触发什么，从开始到结束看到、听到或得到什么。
2. **约束与分工**：必须保留什么、谁拥有业务状态或决定权、复用哪些现有能力；保留用户明确的范围，不自行扩成更大功能。
3. **相关异常**：按实际风险检查拒绝、失败、超时、取消、离开、重复操作、迟到结果及恢复出口，不机械穷举。
4. **完成证据**：怎样证明目标成立，哪些需要测试、真实界面、设备或供应商证据；检查实际有效的动作授权。

能查清的事实和内部实现选择自己处理。只问必须由用户决定的产品行为、风格、范围取舍和缺少的授权。问题给推荐答案及简短理由，不让用户替开发者选择陌生技术细节。

首轮集中少量关键问题，优先使用当前环境可用的提问工具；回答产生新的关键分歧时才追问。已确认的答案持续有效，无回复不视为同意。用户给出的二选一应查证或请其决定，不能擅自改成“两个都做”。没有待决定事项时直接给摘要，不为使用 skill 凑问题。

## 形成一份执行摘要

用用户听得懂的话说明：目标和范围、主要用户行为、推荐实现方向、必须保留的约束、验收方式，以及已授权和仍需授权的动作。技术选择只解释影响结果的部分；小任务几句话即可。

以这份摘要作为后续执行依据，不重复输出长提示词、独立计划和同内容的报告。长期任务复用已有计划和任务记录；用户补充要求时更新原有结论，不从头问一遍。

尚无实施授权时，说明“按这个范围做，可以回复‘开干’；也可以直接修改其中的要求”，然后等待。此时允许继续必要的只读调查，但不能开始实现。

## 收到“开干”后

“开干”“开始做”“按这个做”“直接实施”等表达，按实际语境视为对当前明确范围的实施授权。仅认可方案、要求继续讨论，或引用、示例中的这些词，不自动构成实施授权。若用户同时改了要求，先结合新要求判断；无法确定且会改变结果的关键选择仍需解决，其余独立工作继续。

不要求用户重新复制提示词或逐个点选 skill。先核对当前代码、工作区和已确认摘要有无影响执行的变化，然后连续推进：

1. **实施与验证**：按任务读取 [ui](../ui/SKILL.md)、[test-audit](../test-audit/SKILL.md)；跨端行为使用项目提供的 `cross-layer-behavior`，手机网页平台问题按需使用 `mobile-native`。遇到故障由 `hunt` 定位，不猜测后叠加补丁。
2. **收敛本轮改动**：对有实质内容的修改使用 `patch-audit`，修改后复测受影响部分。任务本身是历史架构减法时使用 `prune`，已完成同等必要性检查就不重复跑两套减法流程。
3. **检查缺陷**：读取 [code-review](../code-review/SKILL.md)，检查正确性、安全和遗漏；在已有实施授权内修复确认的问题并复测。新改动使旧结论失效时只复查受影响范围。独立跨模型审查按明确请求或适用项目规则使用 `adversarial-review`，不自动增加多轮代理。
4. **交付收尾**：按 [check](../check/SKILL.md) 完成适用的发布检查与已授权动作。源码、构建、安装、服务健康和业务验收分别报告，不把其中一项通过当成全部完成。

按风险选检查，小型文案或格式修改不启动整套代码审查、全仓测试和构建。此流程授权读取对应 skill，包括上述代码审查入口；不改变它们在其他任务中的调用策略。先从当前技能目录定位按需能力，缺失时说明限制，用已有能力完成可行部分，不谎称已经运行。

“开干”不扩大提交、推送、部署、生产访问、上传、设备、数据或对外消息的权限。按项目与当前任务的有效授权处理，已有授权不重复询问。只有新的关键产品决定、缺少授权、必要资源或无法取得的证据阻塞时才停下对应部分；继续完成不受影响的工作。

最终简短说明用户会感受到的变化、完成状态、验证证据与未验证部分；给出必要的操作入口。不要仅以“代码已写完”收尾。

## 仅输出提示词

保留上述四方面的完整性检查，可只读补事实；不修改代码，不把提示词里写的动作当成当前授权。

用户要求检查已有提示词时，先简短指出重要缺口，再给一个可复制的完整版本。按任务需要组织目标、用户流程、约束、异常、验收与授权，不强制填满固定模板，不加入用户未表达的新需求。助手补充的假设在代码块外说明。

可在提示词末尾写：“需要我决定的事项，调查后集中问我并给出建议；能查清的自行查证。按已有授权执行，未授权的动作不要提前做。”

用户随后明确要求在当前聊天开始实施时，再按实际范围进入执行；否则以提示词交付结束。
